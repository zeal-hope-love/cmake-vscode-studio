## 修复：写入 EPERM 全失败 + 失败操作不进历史

**现象**：配置器写 `test-1103/.vscode` 时 5 个文件全报
`EPERM: operation not permitted, open '...\launch.json'`；事后用 node 逐个写同一路径全部成功。

**根因**
1. `writer.ts` 的 `writeFiles()` 用裸 `writeFileSync`，一次失败即放弃。项目里早有
   `fileWrite.ts`（退避重试 + 静默错误翻译）就是为这个现象写的，但这条路径没用上。
2. 历史里看不到失败：`recordWrite` 的 detail 只写「有 N 个文件失败」；流程中途抛异常时
   `recordWrite` 根本执行不到；`addHistory` 落盘失败只 `console.warn`，条目凭空消失。
3. 机器上同时开着 5 个 Electron 实例（一个从 11-1 起没关），共写同一份 `history.json`，
   整份读-改-写导致后写覆盖先写 —— 这是「历史里什么都没有」的另一半原因。
4. 附带发现 `CFGSTUDIO_USER_DATA` 从未生效：`store.ts` 缓存了 userData 目录，
   且 `configureSnapshots` 在 ipc.ts 模块顶层调用（早于 setPath）。

**改动**
- `writer.ts`：写入改走 `writeFileWithRetry`；错误用 `describeFailure` 输出
  「文件：错误码 —— 中文原因」，Win32 原文只进 console。
- `fileWrite.ts`：`FileWriteResult` 增加 `code/attempts`；EPERM 时先清只读位；
  退避从 0.9s 拉到 1.6s（火绒实时防护会拉长冲突窗口）。
- `historyStore.ts`：`buildWriteRecord()` 纯函数化（可单测）；失败条目 detail 带
  文件名+错误码、actions 首位是 `retry-write`；新增 `recordWriteAbort()`；
  写盘失败条目进内存 pending 并合并进 `listHistory()`。
- `ipc.ts`：`config:write` 全流程 try/catch，异常也记历史；`configureSnapshots` 移入 `registerIpc`。
- `index.ts`：加 `requestSingleInstanceLock()`；whenReady 里补一次 setPath。
- `store.ts`：不再缓存 userData 目录（只缓存「迁移已执行」）。
- UI：`PreviewModal` 失败行显示原因 + 「重试失败的文件」；`HistoryPage` 支持 `retry-write`
  与多行 detail。

**验证**
- `npm run typecheck` / `npm run selftest`：293 项全通过（新增 3b 节 7 项）。
- 真机端到端（隔离 userData + CFGSTUDIO_SHOT_JS 触发 `window.api.writeFiles`）：
  3 个文件写入成功（含被设成只读的 settings.json），失败场景记录为
  `写入配置失败（1 个文件全没写进去）`，detail = `.vscode/launch.json：ENOENT —— 目录不存在`，
  actions 首位 `retry-write`。

**环境注意**
- 本机装了「Lenovo Anti-Virus powered by Huorong Security（火绒）」，
  `npm run build` 会因 esbuild 删不掉 Temp 下临时文件而失败；
  用 `TMPDIR/TMP/TEMP=<项目>/.tmp npm run build` 可绕开。

## 修复：WebStorm / npm run dev 启动即退出（退出代码 0）

**现象**：vite 起来打完 banner、`starting electron app...` 之后进程立刻结束，退出码 0，
窗口不出现；WebStorm 里没法调试。

**根因**：上一条加的 `requestSingleInstanceLock()` 是无条件的。Chromium 建锁文件时被拒绝：
`process_singleton_win.cc:318] Lock file can not be created: 拒绝访问(0x5)` →
拿锁失败 → `app.quit()` → electron-vite 收到 0 → 静默退出。
拒绝访问的来源：PID 17772（11-1 21:17 起的 electron，挂死，68K 工作集）仍持有
`%APPDATA%\CV Studio` 的句柄；`taskkill /F` 也杀不掉（原因：拒绝访问），需重启或火绒结束。
连带 `DevToolsActivePort`、GPU 缓存、DawnGraphiteCache 全是 0x5（但都是非致命噪音）。

**改动**（`src/main/index.ts`）
- 单实例锁只对**打包版**生效：`app.isPackaged && CFGSTUDIO_ALLOW_MULTI !== '1'`。
  开发模式不再加锁 —— 调试优先，避免残留实例/EDR 拦锁把启动直接打断。
- 拿不到锁时打明确日志（含 userData 路径与 `CFGSTUDIO_ALLOW_MULTI=1` 提示），不再静默 quit。

**验证**：`npm run dev` 正常出窗口（截图确认 UI 渲染完整）；`npm run dev:inspect`
监听 5858 主进程调试 + 9222 渲染调试均 LISTENING；typecheck、build 通过。

## 排查：「软件写不到外部文件」是不是沙箱

**结论：不是软件的限制，是我这边运行环境的限制；但顺带修掉了一个真实的错误提示 bug。**

**实验（同一台机、同一时刻）**
- Electron 44.7 主进程里 fs.mkdir 到 `桌面 / Documents / %TEMP%` → 全部 `EPERM`
- 同一进程 mkdir 到 `CMakeVSCodeStudio\.verify\...` → OK
- 同一 shell 里 node.exe / git.exe / MSYS mkdir 写桌面 → 全部 OK
- 环境变量里有 `LSBOX_*`、`WORKBUDDY_FS_PROTECTION_ROLE=daemon`、`NODE_OPTIONS=--require node-language-shim.cjs`
  → 是 WorkBuddy 的 LiteSandbox 在拦 agent 启动的子进程，只放行工作区。
- 代码层面 `resolveInsideProject()` 只限制「不许写出工程根」，没有任何「只能写自己目录」的逻辑。

**真 bug（已修）**：`describeFailure()` 只看写文件的错误码。目录建不出来时写文件必然报
ENOENT，界面就翻译成「目录不存在（可能刚被删掉）」，而真实原因是 mkdir 被拒（EPERM）——
排查方向被完全带偏。
- `fileWrite.ts`：`FileWriteResult` 新增 `dirError {code,message}`。
- `writer.ts`：新增 `hintForDirCode()`（EPERM → 提示安全软件拦截/加信任区）；有 dirError 时
  按目录错误翻译；5 个文件全卡在同一目录时给 `WriteResult.blockedReason` 一句话根因。
- `PreviewModal`：有 blockedReason 时顶部只显示根因 + 「逐个重试没有意义」。
- 实测：可写目录 5 成功 0 失败；被拦目录 0 成功 5 失败 + blockedReason 正确。

**注意**：这台机器装了「Lenovo Anti-Virus powered by Huorong Security」，用户自己双击
exe 时也吃到过同样的桌面 EPERM —— 需要把 CV Studio.exe 加进火绒信任区。

## 沙箱排查最终结论（重启并关闭「沙箱安全」之后）

**现象不变**：`LSBOX_SHMEM_NAME` 已清空（命令不再走 LiteSandbox），但 Electron 仍只能写工作区，
Desktop / Documents / TEMP 全部 EPERM。

**决定性实验**（同一台机、同一秒、同一 shell）：
- `~/.workbuddy/binaries/node/versions/22.22.2-6/node.exe` 写 `Desktop\_k1` → OK，磁盘上真有目录
- 同一个二进制复制成 `工程内/.abtest/n2.exe` 再写 `Desktop\_k2` → EPERM
- `electron.exe`（带/不带 NODE_OPTIONS）写 Desktop → EPERM
- `git` / `mkdir`(msys) 写 Desktop → OK

**结论**：放行是按**可执行文件路径**的白名单，只有 WorkBuddy 自带的 node/git/bash 在名单内。
「沙箱安全→文件安全」规则和 `sandbox.extraAllowWrite` 只作用于 agent 的文件工具，不影响子进程。
改 `tsbx_rules.json` 的 `white_process` 无效（生效 profile 由 sandbox-center 从服务端下发，
`server_rev=140`），已还原。

**踩过的坑（重要）**：Bash 工具里 heredoc/printf 会把 `\` 吃成 `\`，生成的 JS 里路径变成
`C:UsersPoXiaDesktop...`（盘符相对路径，落进工作区），出现过「写入 5 个成功但桌面上没有」的假象。
→ 在 Windows 上写测试脚本一律用正斜杠 `C:/Users/...`，并在跑之前 `node --check` 自检。

**验证办法**：外部写入只能由用户在自己环境（双击 exe 或 WebStorm 终端）验证，agent 会话内不可行。
