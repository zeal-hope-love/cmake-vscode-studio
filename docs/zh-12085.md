## TL;DR

在 Windows 上，`workspace-write` 会往工作区根的 DACL 上常驻三条记录：一个可继承的 Low 完整性标签、一条 `Everyone` 删除子项拒绝、一个 `S-1-4-*` 能力 SID。其中两条**按设计常驻**——会话结束、DSH 重启、甚至卸载后都还在。**没有任何受支持的关闭方式，没有自定义策略的入口，也没有回收手段。**

这篇请求的是一个**配置开关**，不只是修 bug。其他报告（#9649、#11193、#10676、#10951…）记录的是造成的损害；这篇要的是让"理解了取舍的用户能够避开它"的那个控制面。

我建议做成**两个独立开关**，因为两者风险差别很大，维护者完全可以接受其中一个而拒绝另一个：

- **A —— 进程约束**（受限令牌 / Low 完整性令牌）。这才是真正约束 agent 的部分。去掉它是实打实的安全回退，所以必须显式、醒目、按会话。
- **B —— 工作区树打标**（树上那个可继承的 `OI|CI` Low 标签）。**这部分才是让人难受的，而拿掉它对维护者几乎没损失**——见第 4 节，这个论证其他帖子里没有人提过。

## 1. 环境

- Windows 11 `10.0.26200`，DSH 桌面端（Electron），当前用户级安装
- 工作区：`<user>\Desktop\<workspace-root>` —— 一个多项目根目录
- 主项目：Electron + electron-vite + React 桌面应用（`npm run dev`、`npm run build`、`npm run dist`）
- 同一个根下还有若干 C/C++ 固件工程（GCC 交叉工具链、Ninja、某厂商代码生成器）

## 2. 沙箱写了什么、什么留下了

标签生效期间在工作区根上观测到：

```
Everyone:(CI)(DENY)(DC)
S-1-4-275285986-556314953:(OI)(CI)(W,D,DC)
Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)   ← 关键的就是这条
```

`packages/sandbox/sandbox-local/src/index.ts:406-416` 以 `standing = true` 调用 `materializeAclGrant(workspaceRoot)`，紧随其后的 catch 块明确写着：常驻 ACE "is the intended end state, not an error artifact — nothing to revoke."（是预期终态，不是错误残留，无需回收）。而 `AclWriteGrant.dispose()`（grant.ts:116-140）只回收 `revocablePaths`，`standingPaths` 原样留下。

所以：**按设计，永久，且用户无法撤销。** 维护者在文档里已经这么说了；本篇请求的是——把"永久"变成一个选项，而不是"打开一个文件夹"的无条件后果。

## 3. 为什么这对真实工程代价这么大（我的实际状态）

### 3.1 构建产物把自己污染了

树上产出的每一个 `.exe` 都会继承标签。我当时在本机实测：**项目下 40 个可执行文件，40 个都是 `Low`**，包括 `node_modules\electron\dist\electron.exe`。

做了一组干净的对照实验——同一个二进制、同一个父进程，只换目录：

```
<workspace-root>\proj\.tmp                LOW(4096)      ← 树内
<workspace-root>                          LOW(4096)      ← 工作区根
<other-dir>                               Medium(8192)   ← 工作区外
<user>\AppData\Local\Temp                 Medium(8192)   ← 工作区外
```

于是 `npm run dev` 拉起的 Electron 主进程跑在 **Low**，它写不了自己的 `%APPDATA%` 配置，也写不了目标工程目录：

```
EPERM: operation not permitted, open 'C:\Users\<user>\AppData\Roaming\<app>\probe.txt'
```

而**打包后的版本一切正常**——它装在 `%LOCALAPPDATA%\Programs\` 下。同一份源码、同一个 Electron 版本，唯一差别就是镜像文件上的完整性标签。

**这个不对称是我最难受的地方**：它让打包出来的产品看着好好的，只有开发循环是坏的。所以人第一反应是"我的开发环境配坏了"，而不是"沙箱干的"。

### 3.2 部署清理失败

`electron-builder` 清理旧产物、把旧的 `release\` 目录挪进回收站，都会撞上 `Everyone:(CI)(DENY)(DC)` 那条（`genie-trash: Some operations were aborted`）。我只能退回沙箱外执行 `Remove-Item -Force`——那等于把这条 deny 本来想防的东西也绕过去了。

### 3.3 它不可见，而且会自己回来

- `Get-Acl` 根本不显示强制标签；常规的"右键 → 属性 → 安全"看到的是一份完全正常的 ACL。只有 `icacls` 能看到，而没有任何东西提示用户去看。
- 失败形式是 `EPERM`，读起来像"文件被占用 / 只读"。
- 任何手工清理都会在下一次供给时被覆盖——且没有任何提示（#9649 也提了这点）。

### 3.4 我现在的两个选项都很难受

| 选项 | 代价 |
| --- | --- |
| `danger-full-access` | 连**文件防护**一起关掉，不只是进程约束。我丢掉的恰恰是我想要的那层保护。 |
| `read-only` | 根本没法干活。 |
| 每次供给后手工 `icacls` | 无法可靠自动化；`S-1-4-*` 这个 SID 用 `icacls /remove` 删不掉（`ERROR_NONE_MAPPED` 1332）。 |

没有第四个选项。这就是缺口所在。

## 4. 让标签可配置的安全论证

这是我最希望维护者考虑的部分，因为它颠倒了"关掉沙箱特性 = 更不安全"的直觉。

**给树打标，让工作区里的可执行文件变得*更不受保护*，而不是更受保护。**

- `.exe` 若保持 `Medium`：受限于 Low 的 agent 子进程受 `SYSTEM_MANDATORY_LABEL_NO_WRITE_UP` 约束，**无法覆盖它**。
- 标签被继承后：`.exe` 变成 `Low`，Low 的 agent 子进程**可以**覆盖它。
- 而用户随后会以 `Medium` 身份运行这个二进制——双击、`npm run dev`、安装器、同一棵树上的 CI。

也就是说，当前策略授予了受限进程一项它本不该有的能力：**改写用户稍后以 Medium 完整性运行的可执行文件。** 这是一个新的写入面，而且是由约束机制自己制造出来的。

因此，从树上摘掉标签——同时保留受限令牌——**不是**纯粹的放松。在对抗这条威胁的维度上，它是**加固**。真要说的话，"不给可执行文件打标"本身就是一个加固建议，配置开关只是把它暴露出来的自然方式。

（讲清楚一点：我不是在论证整个沙箱净收益为负。令牌约束确实在干活。问题**具体地**出在*可继承的树标签*上，它的成本收益在开发型工作区里算不过来。）

## 5. 方案

### 5.1 我希望的配置面

插件层的东西，类似：

```yaml
- id: sandbox
  config:
    windowsAcl:
      # 哪些对象获得可继承的 Low 标签。默认值保持今天的行为。
      integrityTargets: ['agent-scratch']   # | 'workspace'（当前行为）| 'none'
      # agent-scratch 放在哪（由 DSH 创建和管理，不碰用户的树）
      scratchDir: '.dsh/sandbox'            # 相对工作区根
      # 保留常驻的 ACL 授权（agent 写工作区所需）
      workspaceGrant: true
      # 回收命令，见 5.2
      allowRelease: true
```

核心想法：**把"agent 可以写这个工作区"和"工作区树是 Low 完整性"这两件事分开。** 它们现在被焊死在一起，而只有前者是 agent 能干活所必需的。

`integrityTargets: 'agent-scratch'` 意味着只给 agent 专用于临时工作的那个子目录打标，构建产物保持环境原有的完整性——同时受限令牌依然限制 agent 自身进程能写什么。

### 5.2 回收路径（无论 5.1 是否实现都需要）

```
dsh sandbox status  [--workspace <dir>]   # 显示标签 / SID / 拒绝条目
dsh sandbox release [--workspace <dir>]   # 移除标签 + S-1-4-* ACE + Everyone 拒绝
```

文档已经指出，手工 `icacls` 删 `S-1-4-*` 这个 SID 会以 `ERROR_NONE_MAPPED`（1332）失败。**工具能写进去，就应该能删出来**；让用户自己在 PowerShell 里重新实现一遍，是当前体验里最糟的部分。

### 5.3 最低限度的降级方案

如果完整的策略配置超出范围，下面这些已经能去掉我大部分的痛：

1. **`dsh sandbox release`** —— 哪怕只针对工作区根，哪怕下次供给还会重新施加。它把"不可恢复"变成"烦但能恢复"。
2. **不要让可执行文件继承标签。** 在 `grantWrite` 之后，把 `*.exe`、`*.dll`、`*.node` 重置为 `Medium`。代价：新构建出来的二进制需要再次纠正，所以要么供给时重扫，要么用目录监视。
3. **供给时警告**——当工作区已包含或将要包含可执行文件时，给一行说明和恢复命令。内置的 `diagnose-windows-sandbox-acl` 诊断技能是天然的位置。
4. **拒绝卷根和驱动器根**——在写入任何东西之前（#11193）。属于同一类"破坏性编辑之前先做目标校验"。

### 5.4 关于"设计如此 / 文档已记录"

我想在这里对维护者公平一点。README 已经承认了：

> 诊断保留完整性标签——它无法修复 Low 标签的可执行文件影响用户在 DSH 外启动程序的问题

这是承认**目前修不了**，不是承认**不需要修**。一个副作用——用户完全看不见、自助恢复不了、卸载后仍永久附着在用户文件系统上、并且会静默打断任何会编译出可执行文件的项目的开发循环——这就是需要一条受支持的逃生通道的理由，哪怕今天所有默认值一个字都不改。

## 6. 为什么要配置开关，而不是只改默认值

我不认为默认值就一定要改——在不可信仓库上跑只读或 `workspace-write` 的 agent 是真实场景，标签对*源文件*确实是有效的加固。问题在于，同一个机制被**无条件**施加到了**用户因为信任才选中的那个目录**——他自己的项目根上。

只有用户自己知道某个文件夹是一次性 clone 还是要发布的那个应用的工作副本。这个不对称，正是配置开关存在的理由。

说得具体点：我不是在要一个换了名字的 `danger-full-access`。我要的是 `workspace-write`（文件防护开着、agent 不能乱跑）**减去**那个把我编译器产出的每一个二进制永久降级的部分。
